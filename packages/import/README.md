# @barbearia/import

Spike do **importador MySQL → Postgres multi-tenant** (Fase 7 do SAAS_PLANO,
tratada como ferramenta de venda: "migre sua barbearia em 5 minutos").

## O que existe (testável sem banco)

1. **`parse-dump.ts`** — parser mínimo dos INSERTs do dump phpMyAdmin
   (`sql/barbearia.sql`): colunas explícitas, strings com escaping do MySQL
   (`\'`, `\\`, `\"`), `NULL` → null, números tipados. Linha com contagem de
   valores errada lança erro (defesa).
2. **`map.ts`** — mapeamento puro para o schema Postgres de `packages/db`:
   - `tenant_id` injetado em toda linha de toda tabela;
   - sentinela `'0000-00-00'` → `null` nos campos de data mapeados (clientes,
     receber, pagar, agendamentos — o Postgres rejeita data zero);
   - `dias.dia` normalizado via `@barbearia/domain` (`'Sabado'` → `'Sábado'`,
     o bug do legado);
   - `id` da origem preservado (identidade `GENERATED BY DEFAULT` do schema
     aceita ids explícitos — a migração mantém as referências por convenção);
   - flags `'Sim'/'Não'` preservadas como text (fiel ao schema atual).

O teste de integração roda o pipeline inteiro contra o **dump real**
(`sql/barbearia.sql`): 15 tabelas, contagens exatas, remaps, desescape do
iframe da config.

## Fluxo em produção (próximo passo)

```
MySQL ao vivo (SELECT por tabela)
   → mapearImportacao(tenantId, tabelas)   [este pacote — lógica de conversão]
   → INSERT/COPY no Postgres dentro de uma transação com RLS do tenant
   → revalidar contra as regras de @barbearia/domain (ex.: conflitos de agenda)
```

O leitor da fonte muda (SELECT no MySQL em vez de parser de dump), mas o
mapeamento é o mesmo — por isso ele é o coração testável.
