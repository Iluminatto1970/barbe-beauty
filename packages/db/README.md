# @barbearia/db

Schema **Postgres multi-tenant** (Drizzle ORM). Alvo em produção: **Neon**.

## Status

As **21 tabelas do MySQL** (`sql/barbearia.sql`) foram mapeadas para o Postgres em
`src/schema.ts` (+ `tenants`), com:

- `tenant_id` (uuid, FK → `tenants`) em **toda** tabela de negócio;
- **RLS** por tenant: policy `tenant_isolation` em cada tabela
  (`tenant_id = current_setting('app.tenant_id', true)::uuid`);
- **FKs reais** (o MySQL não tinha nenhuma — 49 referências no total);
- `id` como **identity** `GENERATED BY DEFAULT` (permite inserir ids explícitos na
  migração de dados);
- invariante de domínio no banco: **unique** `(tenant_id, funcionario, data, hora)`
  em `agendamentos` (slot único por funcionário/dia — o conflito da regra de negócio);
- `usuarios.email` unique por tenant;
- `clientes.data_nasc` e `pagar/receber.data_pgto` como NULLABLE (o MySQL aceitava
  `'0000-00-00'`, que o Postgres rejeita — a migração mapeia para NULL).

## Uso

```bash
# 1. Gerar o SQL de migração a partir do schema
pnpm db:generate          # → drizzle/0000_*.sql (tabelas, FKs, policies RLS)

# 2. Aplicar (requer DATABASE_URL, ex.: postgres://...@neon.tech/...)
pnpm db:migrate

# 3. Ativar RLS nas tabelas (o drizzle-kit desta versão não emite o ALTER)
psql "$DATABASE_URL" -f sql/02-enable-rls.sql

# 3b. Superadmin do SaaS (role com BYPASSRLS p/ o /admin enxergar todos os tenants)
psql "$DATABASE_URL" -f sql/03-saas-admin.sql

# 4. Abrir o Drizzle Studio
pnpm db:studio
```

## Superadmin (/admin do produto)

O RLS isola tenants até do operador. Para o `/admin` (suporte, migração, cobrança)
rodar SEM escopo de tenant, crie a role **`saas_admin`** com `BYPASSRLS`
(`sql/03-saas-admin.sql`) e conecte o admin com um usuário que herde dela. O admin
NÃO chama `definirTenant()`; as rotas normais continuam com RLS.

> **Dev local sem Postgres**: o `apps/web` roda com **pg-mem** (in-memory) quando
> `DATABASE_URL` não existe — o seed (`apps/web/lib/seed.ts`) cria as tabelas e
> carrega o dump real do legado (`sql/barbearia.sql`) via `@barbearia/import`. Nesse
> modo o RLS não roda (pg-mem não suporta policies); o isolamento fica por
> `tenant_id` em toda query (`apps/web/lib/repo.ts`) — em produção o RLS é a
> segunda barreira.

## RLS na aplicação

Toda transação que acessa dados de tenant precisa definir o contexto antes:

```ts
import { definirTenant } from '@barbearia/db';

await db.execute(definirTenant(tenantId)); // escopo da transação
const agendamentos = await db.select().from(agendamentos); // só o tenant ativo
```

- O **owner** do banco (migrações/seed) ignora RLS.
- A aplicação conecta como **`authenticated`** (role não-superuser).
- Com pooling (Neon/PgBouncer), `set_config(..., true)` mantém o contexto na
  transação — defina em toda transação, nunca fora dela.
